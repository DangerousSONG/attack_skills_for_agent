# RFC 9000 §10.3 Stateless-Reset Token Secrecy and Uniqueness Audit

## 1. Normative Clauses (Original Sources)

RFC 9000 §10.3.1: the stateless-reset token is generated by the endpoint for every connection ID it issues (randomly or derived as `HMAC(static key, connection ID)`); the token **must be kept secret** — any adversary able to predict the token can reset the corresponding connection.

RFC 9000 §10.3.2 (key points):
> Two connection IDs **must not** be assigned the same stateless-reset token (collisions within the same endpoint must be avoided — a false match kills an innocent connection).

RFC 9000 §10.3.3: when the receiver matches a reset token on a short-header packet that cannot be associated with any active connection, it **must** enter the draining state and discard connection state.

RFC 9000 §21.11: stateless resets create a "TCP-reset-injection"-like DoS class — implementations must avoid constructing a **Stateless Reset Oracle** (where an attacker can borrow a third-party server to probe token states); multi-backend deployments sharing one reset key + nondeterministic routing are the necessary condition for this attack.

Core pattern in one sentence: **the 16-byte token is the power of life and death over a connection — it needs no cryptographic break, only to be derived, leaked, or reused; anyone who can place it at the end of a UDP packet can silently kill an encrypted connection.**

## 2. Violation Criteria

| ID | Probe | Criterion |
|---|---|---|
| SR-1 | Collect multiple connection IDs across rotations from the same endpoint; analyze whether a derivable relationship exists between token and CID (e.g., token = F(CID) with F reconstructible from public header fields) | A derivable relationship exists → violation (CVE-2026-50009 Netty empirical: the HMAC construction lacked domain separation, and rotated-CID bytes leaked the old token) |
| SR-2 | Verify whether token generation performs key domain separation: whether CID generation and token generation share the same HMAC context/input | No domain separation → high risk |
| SR-3 | Probe the token-collision strategy: actively trigger multiple CID rotations within one connection and count whether tokens are unique | Duplicate tokens appear → violates §10.3.2 |
| SR-4 | Send a forged Stateless Reset packet to an active connection (correct 16-byte trailer + unassociable short header); observe whether it is accepted | Acceptance is protocol-compliant behavior, but confirming the acceptance path has no source-address validation is a record item; whether the send path rate-limits/prefix-checks is the audit point |
| SR-5 | Deployment-surface probe: with multiple backends sharing a reset key + nondeterministic routing, can a token obtained from backend A take effect on backend B | Takes effect → Stateless Reset Oracle established |
| SR-6 | Send a stateless-reset packet carrying an old token of an already-destroyed/just-closed connection; observe the implementation (xquic empirical pattern) | NULL-pointer dereference / crash → violation |

Method: long-lived connections to capture CID-rotation sequences + token observation (requires on-path or same-host testing); aioquic to construct forged reset packets; multi-backend routing tests.

## 3. Attack-Surface Hypotheses

- **Targeted connection killing (DoS)**: SR-1/SR-5 — on-path or oracle scenarios enable unauthenticated killing of arbitrary connections; devastating for long-connection services (real-time audio/video, financial push feeds)
- **Reset reflection**: attackers use third-party servers' reset responses for reflection/probing
- **Unauthenticated crash**: SR-6 — the token-match path sits on the connection-lookup-failure branch; interaction with already-destroyed connection state is a high-frequency fuzz crash area

## 5. Differential Verification

Control group: quic-go ≥ 0.60 (random tokens + independent keys), Netty ≥ 4.2.15.Final, msquic.
Comparison fields: SR-1 derivability, SR-2 domain separation, SR-3 collision rate, SR-6 destroyed-connection tolerance, SR-5 deployment surface.
False-positive exclusion: random per-CID token generation is compliant; an `HMAC(static, CID)` construction with domain separation and a non-derivable key is also compliant; only flag "derivable", "collisions", and "shared key + nondeterministic routing".
